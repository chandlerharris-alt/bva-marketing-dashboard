## Fixed: newly-granted users saw no tabs (likely stale-cached access.json in /api/me)
Reported: Chandler added several users to access.json via the Admin panel, but they landed on a bare Overview with no sidebar tabs and no way to see anything else. Traced the whole path (`initAuth()` -> `/api/me` -> `applyAuthToUi()`'s `isGranted` check -> `renderAccessDenied()`) — this is exactly the "Access Not Granted" panel firing (it hides `aside.sidebar`/topbar/filterbar but never explicitly hides Overview's own render target, which is why residual Overview content can still be visible underneath — explains the "stuck on Overview" description even though the real state is "denied, not unlisted-in-practice").

## Fixed (real root cause): non-admin users with full tab access still saw no sidebar tabs
The cache fix above wasn't the whole story. Chandler tested it precisely: made michael.doran@ifit.com admin (worked, saw tabs) → removed admin and instead checked every capability box on both tabs individually (`marketing`+`media`, all caps true, `admin:false`) → tabs disappeared again. That isolated it to the non-admin code path specifically, not caching.
- **Root cause**: `applyAuthToUi()`'s `isGranted` check was `AUTH_STATE.admin || (MANIFEST?.tabs||[]).some(t => authCanSee(t.slug))` — it cross-referenced the user's granted tabs against the global `MANIFEST` object. But `MANIFEST` loads via a 3-round-trip chain (`_domain_config.json` → `version-visibility`/`rev-aop` → `manifest.json`) while `/api/me` (which triggers `applyAuthToUi()`) is a single round trip and virtually always resolves first. So for any non-admin user, this check ran against `MANIFEST?.tabs` = `undefined` → `[]`, `.some()` on an empty array is always `false` → `isGranted` was `false` → `renderAccessDenied()` fired for every non-admin user regardless of their actual access. Admin users never hit this because `AUTH_STATE.admin` short-circuits the check entirely — which is exactly why "make him admin" fixed it and "give him full caps without admin" didn't; that A/B was the tell.
- **Fix**: `isGranted` no longer references `MANIFEST` at all — it now checks whether `AUTH_STATE.tabs` (the user's own granted caps, already returned by `/api/me`) has any tab with any capability true. This can never race against the manifest load.
- **Second, related bug found in the same area**: `filterSidebarByAccess()` (which hides individual sidebar tab wraps a user lacks caps for) is only ever called from `applyAuthToUi()`, which — same timing issue — usually runs *before* `renderSidebar()` has created any `.manifest-tab-wrap` elements yet. It was a silent no-op on zero elements, and nothing re-ran it after `renderSidebar()` populated the sidebar, so a since-restricted tab could stay visible. Fixed by also calling `filterSidebarByAccess()` right after `renderSidebar()` in the manifest-load chain, so whichever of the two async chains (`/api/me` vs manifest) finishes last still gets the correct final filter applied. (This hadn't been noticed before because the manifest currently has only 2 tabs, `marketing`/`media` — most granted users have `view` on both, so under-filtering was invisible; it would only ever show up as an *unintended extra* tab, the opposite of what Michael hit.)
- Verified directly in preview by forcing the exact race (`MANIFEST = null` at the moment `applyAuthToUi()` runs) with Michael's real access.json entry (admin:false, full caps on both tabs) — no access-denied panel, sidebar stays visible. Also verified `filterSidebarByAccess()` correctly hides a tab the test user has zero caps on and leaves a fully-capped one visible.
