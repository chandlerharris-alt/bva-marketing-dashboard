## Mobile optimization pass (all features)
Chandler asked for the whole dashboard optimized for mobile. Before this, the app had a viewport meta tag and a handful of incidental `@media` tweaks for a few KPI/chart grids, but no real responsive strategy — the sidebar, filterbar, tables, and modals were all fixed-width with no breakpoint at all.

**Scope insight that kept this from being a huge per-feature effort**: every tab/view (OPEX, Media, Overview, Forecast, Users, Data Controls, Reclass Suggestions, every drill/expansion panel, every modal) shares the same handful of CSS classes (`.sidebar`, `.shell`, `.filterbar`, `.bva`, `.modal-backdrop`, `.chart-canvas-wrap`). Fixing those shared classes at the CSS level, in one `@media (max-width:768px)` block near the end of the `<style>` block, improves every feature at once — no table-building function (`buildTable`, `buildMediaGrid`, `buildCompanyBvATable`, etc.) needed to change.

**What changed, all under `@media (max-width:768px)` unless noted:**
- **Sidebar → off-canvas drawer.** Was `position:fixed; width:230px` permanently reserving 61% of a 375px screen with zero collapse mechanism. Now `transform:translateX(-100%)` by default, `.sidebar.open{transform:translateX(0)}`, `.shell{margin-left:0}` so content takes the full width. New hamburger button in the topbar (`.sb-hamburger`, hidden above the breakpoint) calls `toggleSidebarDrawer()`. A `#sidebar-backdrop` overlay appears behind the open drawer and closes it on click. Every real navigation entry point (`loadTab`, `loadOverview`, `loadAdmin`, `loadReclassView`, `loadDataControlsView`) calls `closeSidebarDrawer()` on entry — since region sub-tabs and the Admin dropdown's Users/Data Controls both route through `loadTab()`/`loadAdmin()`/`loadDataControlsView()`, this one call per function covers every sidebar item without touching each `onclick` individually.
- **Filterbar → collapsible.** Was already `flex-wrap:wrap` (reasonable) but up to 12 fields at 170px min-width each would wrap into 4-6 rows eating the whole screen above the fold. Now hidden by default (`.filterbar{display:none}` / `.filterbar.open{display:flex}`) behind a small always-visible "⚙ Filters" toggle button (`toggleFilterbar()`), and `select`/`.multisel-trigger` min-width drops to 130px so two fields fit per row once expanded.
- **Tables → sticky first column + scroll cue.** `.bva-wrap{overflow:auto}` already existed (a real horizontal-scroll wrapper), but `white-space:nowrap` cells meant the category/account label scrolled off-screen with the rest of the row. Now the first `<th>`/`<td>` gets `position:sticky; left:0; background:inherit` so the label stays put while scrolling through value columns — pure CSS (`.bva tr>*:first-child`), no table-builder changes, since every builder already emits the label as the first cell. Added a subtle right-edge gradient on `.bva-wrap` as a scroll-affordance cue, and tightened font-size/padding for density.
- **Modals → fit the viewport.** `.modal{min-width:480px}` overflowed a 375px screen. Now `min-width:0 !important; width/max-width:calc(100vw - 32px)` under the breakpoint — the `!important` is specifically needed to beat the Slide Deck modal's own inline `min-width:420px`, which a plain class rule can't override.
- **Charts → viewport-aware height.** `.chart-canvas-wrap` fixed heights (340px/400px tall) made charts disproportionately tall on a narrow screen even though Chart.js itself was already correctly `responsive:true, maintainAspectRatio:false` everywhere. Dropped to 240px/280px under the breakpoint.

**A real testing-environment gotcha worth remembering for next time**: the local sandboxed preview browser used for verification has a genuine rendering bug where `transition:transform` on an element silently prevents subsequent `transform` changes from ever visually/computationally taking effect (confirmed via an isolated minimal repro — removing only the `transition` property made an otherwise-identical class toggle work instantly; this reproduces with plain vanilla CSS unrelated to this app's code). Diagnosed by testing with `transition:none` temporarily, which confirmed the actual shipped CSS/JS (`toggleSidebarDrawer()` + `.sidebar.open`) is correct — real browsers handle `transition:transform` normally, so the shipped code keeps its slide-in animation. If a future mobile verification pass sees a toggle silently "not working" in this same local preview, check for a `transition` on the animated property before assuming the code is broken.

**Verified**: at true 375px width, `document.body.scrollWidth === window.innerWidth` (zero page-level horizontal overflow) on every view checked — OPEX, Media, Overview, Data Controls, Reclass Suggestions — with the wide `.bva` tables scrolling only inside their own `.bva-wrap`. Sidebar drawer open/close, filterbar collapse/expand, sticky first column, modal width (343px = 375-32, exact), and chart height (280px, down from 400px) all confirmed via computed-style checks. Re-verified at 1280px desktop width that every one of these reverts to its original pre-existing behavior (sidebar back to fixed 230px always-visible, filterbar always-visible, table font-size/position back to normal, modal back to 480px min-width) — the whole pass is breakpoint-scoped with no bleed into desktop.

## Fixed: category tags saved by one person were invisible to everyone else (incl. incognito)

## Fixed (real root cause): non-admin users with full tab access still saw no sidebar tabs
The cache fix above wasn't the whole story. Chandler tested it precisely: made michael.doran@ifit.com admin (worked, saw tabs) → removed admin and instead checked every capability box on both tabs individually (`marketing`+`media`, all caps true, `admin:false`) → tabs disappeared again. That isolated it to the non-admin code path specifically, not caching.
- **Root cause**: `applyAuthToUi()`'s `isGranted` check was `AUTH_STATE.admin || (MANIFEST?.tabs||[]).some(t => authCanSee(t.slug))` — it cross-referenced the user's granted tabs against the global `MANIFEST` object. But `MANIFEST` loads via a 3-round-trip chain (`_domain_config.json` → `version-visibility`/`rev-aop` → `manifest.json`) while `/api/me` (which triggers `applyAuthToUi()`) is a single round trip and virtually always resolves first. So for any non-admin user, this check ran against `MANIFEST?.tabs` = `undefined` → `[]`, `.some()` on an empty array is always `false` → `isGranted` was `false` → `renderAccessDenied()` fired for every non-admin user regardless of their actual access. Admin users never hit this because `AUTH_STATE.admin` short-circuits the check entirely — which is exactly why "make him admin" fixed it and "give him full caps without admin" didn't; that A/B was the tell.

## Variance Investment/Divestment tab: 3 real bugs found + fixed (2026-07-29)
Chandler's report: "nothing for June in Paid/Non-Paid media" and "showing massive favorable variance for OPEX in June that does not match the OPEX tab." Investigated by directly comparing `computeVarianceRegionData()`'s output against the real OPEX tab's own on-screen June/July totals (Month view) — found three distinct, compounding bugs, all now fixed and re-verified to match the OPEX tab to the dollar:

1. **Wrong default Plan version for the fiscal year.** `varDefaultPlanVersion()`'s `names.find(v => /AOP Final/i.test(v))` matches the FIRST name in the (alphabetically-sorted) available-versions list containing "AOP Final" — for FY2027 that's **`FY26: AOP Final`**, not `FY27: AOP Final` (`'6'` sorts before `'7'`). FY26's AOP has essentially no real FY2027 monthly data (only whatever `applyPrepaidToForecasts()`'s cross-FY spillover injects), so every region's Plan came out near-zero or wrong for that fiscal year. **Fix**: reused the exact pattern `setupComparisonPickers()` already uses for this identical problem — prefer a version name that `startsWith('FY' + (fy-2000))` before falling back to any `/AOP Final/i` match.
2. **Forecast $ per company need FX conversion, same as actuals — CORRECTED (see follow-up below, this was gotten wrong on the first pass).** `varForecastMonthly()` originally FX-converted every company's forecast array, same as the actuals path. Removing that conversion happened to make the **blended, all-regions June total** match the OPEX tab's total exactly ($1,256,675) — but that "match" only held because the US company's FX rate is exactly `1.0` and the US dominates the total; it wasn't evidence that Plan $ are USD-native. See the dated follow-up entry below for the real root cause and the corrected fix (FX conversion restored).
3. **Revenue's forecast has no per-company breakdown at all**, so it was always $0 in this tab — which nulled out every advertising rate-of-sales variance for the month (the "nothing for June" symptom specifically), since a null revenue% makes `varRateVariance()` skip the month. - **`applyPrepaidToForecasts()` refactored** to take an optional `dataset` param (defaults to global `DATA`), same reasoning as `fxRate()`'s existing `srcData` param — `loadVarianceTabView()` now calls `applyPrepaidToForecasts(VARIANCE_DATA)` right after fetching, so this tab's Plan figures get the same cross-FY prepaid spreading as the main grid instead of raw un-amortized lump sums.

## Follow-up same day: forecast $ DO need per-company FX conversion — deeper, app-wide finding
Chandler's next question after the fixes above: "Are you converting to USD on all of the regions? I don't think we have $146k in China in salaries in June." He was right — and the investigation turned up something bigger than the Variance tab.
- **China's Fixed OPEX Plan for June was $146,601**, almost entirely one account: `8010000 Payroll Expense` at $135,007.78 — the SAME raw number the real OPEX tab's own **China region sub-tab** shows for that line (confirmed by actually clicking into the China sub-section and rendering it). - **Real root cause, one level deeper than the Variance tab**: `getSeries()`'s own company-filtered branch (used by, e.g., Overview) already divides by `fxRate()` for exactly this reason — the correct convention already exists in the codebase. But **`effectiveSeries()`** (what the main OPEX region sub-tabs actually call) routes through `channelForecastMonthly()` instead whenever `STATE.selectedChannels` is set — and it's *always* set to "every channel" as soon as any tab loads (`rebuildChannelOptions()` populates it unconditionally), even though the channel selector itself is UI-hidden on OPEX. `channelForecastMonthly()` has no FX step at all. So **every OPEX region sub-tab (China, UK, Canada, Mexico, Australia, EMEA) is showing raw, un-FX-converted local-currency Plan figures today** — this is a pre-existing bug in the main app, not something introduced by the Variance tab work, just surfaced by it.
- **Why the earlier "Fixed OPEX $ don't need FX" fix (item 2 above) looked correct at first**: the blended, all-region June total matched the OPEX tab's grand total either way, but only because the US company's FX rate is exactly `1.0` and the US is the overwhelming majority of the total — a non-USD region's error doesn't move a US-dominated blend by much in absolute dollars, even though it's wildly wrong for that region specifically. Testing against the blended total instead of a specific region masked the bug.
- **Fixed in the Variance tab**: `varForecastMonthly()` now divides by `fxRate(c, fy, i+1, VARIANCE_DATA)` again for the `forecasts_by_company` path (matching `varActualsMonthly()`'s existing convention) — the revenue fallback path (RPT_FORECAST_DETAIL, which stores `AMOUNT_USD` directly) correctly stays unconverted. ## Paid Media rate variance now computed per channel, not blended per region
Chandler's ask: Paid Media's "rate of sales" variance should be computed **per channel** against that channel's own revenue — his example: `(DTC US % of revenue planned × DTC US actual sales) − DTC US actual ad spend` — then summed to the region. Blending all channels' ad spend against one region-wide revenue number (the old approach) meant a channel with an outsized ad-spend-to-revenue rate (e.g. Wholesale, which typically carries little/no paid digital spend of its own) got diluted against a channel with a very different rate (DTC), producing a number that didn't reflect any one channel's real efficiency. Non-Paid Media stays region-level, per Chandler's explicit instruction (it isn't targeted at one channel's sales the way paid digital spend is).
- **New channel-scoped helpers**: `varRawChannels()`/`varChannelGroups()` (own cache against `VARIANCE_DATA`, mirrors `mktgRawChannels()`'s approach for the global `DATA` — can't reuse that one directly since it caches against a different dataset) group every raw channel value found in the data under its normalized display name via the existing `mktgNormChannel()`. `varActualsMonthlyChannel()`/`varForecastMonthlyChannel()` slice actuals (from `actuals_by_channel_company`) and forecast (scanning `forecast_lines` directly by `.channel` — `forecasts_by_company` has no channel dimension at all) to one company set **and** one channel group, with the same per-source FX convention `varForecastMonthly()` already established (PLANNING_GENERAL lines divide by `fxRate()`; RPT_FORECAST_DETAIL revenue lines don't, they're already USD).
- **`computeVarianceRegionData()` rewritten**: for Paid Media, loops every display channel (Wholesale/DTC/Freemotion/iFIT-Core/iFIT-App/Corp-Other), computes `varRateVariance()` against that channel's own plan/actual ad spend and plan/actual revenue, then sums the six channels' dollar variances into the region total (`paid_media.byChannel[channel] = {plan,actual,variance,bps}` kept for potential future per-channel drill-down UI). Non-Paid Media's call is untouched — same whole-region `varRateVariance()` as before.
- **Cleanup**: removed a dead line in `renderVarianceTabView()` (`metricNote`, computed but never actually inserted into the returned HTML — confirmed unused earlier) that would have thrown once `paid_media` stopped carrying a top-level `.bps` array.
